# Day 07 – Linux File System Hierarchy & Scenario-Based Practice

---

## Part 1: Linux File System Hierarchy

### Core Directories (Must Know)

#### `/` – Root
The top-level directory; every other directory and file lives under it. Running `ls -l /` shows directories like `bin`, `etc`, `home`, `var`, `tmp`, and more.
**I would use this when** navigating to any part of the filesystem from scratch or writing absolute paths in scripts.

---

#### `/home` – User Home Directories
Stores personal directories for each non-root user (e.g., `/home/alice`, `/home/bob`). Running `ls -l /home` shows one folder per user.
**I would use this when** looking for user-specific config files, scripts, or uploaded files from a developer.

---

#### `/root` – Root User's Home
The home directory specifically for the `root` (superuser) account — separate from `/home`. Running `ls -la /root` may show `.bashrc` and `.bash_history`.
**I would use this when** I'm logged in as root and need to store or find root-owned scripts or config.

---

#### `/etc` – Configuration Files
System-wide configuration files live here (e.g., `/etc/hostname`, `/etc/ssh/sshd_config`, `/etc/fstab`). Running `ls -l /etc` shows hundreds of config files and subdirectories.
**I would use this when** troubleshooting a misconfigured service or changing system-level settings.

---

#### `/var/log` – Log Files
Contains logs generated by the OS, services, and applications (e.g., `syslog`, `auth.log`, `nginx/access.log`). Running `ls -l /var/log` shows files like `syslog`, `kern.log`, `dpkg.log`.
**I would use this when** a service crashes or behaves unexpectedly — logs here tell me what went wrong.

---

#### `/tmp` – Temporary Files
Holds temporary files created by applications and users; cleared on reboot. Running `ls -l /tmp` may show session sockets or scratch files.
**I would use this when** I need a quick scratch space to download or extract something without worrying about cleanup.

---

### Additional Directories (Good to Know)

#### `/bin` – Essential Command Binaries
Core commands needed even in single-user/recovery mode (e.g., `ls`, `cp`, `bash`). Running `ls -l /bin` shows fundamental Unix utilities.
**I would use this when** verifying that a basic command exists or writing minimal shell scripts for recovery.

---

#### `/usr/bin` – User Command Binaries
Most installed application binaries live here (e.g., `git`, `python3`, `curl`). Running `ls -l /usr/bin` shows a large list of user-facing tools.
**I would use this when** checking if a tool is installed on the system or finding the path for a `shebang` line in scripts.

---

#### `/opt` – Optional/Third-Party Applications
Self-contained third-party software (e.g., custom agents, proprietary tools) is installed here. Running `ls -l /opt` may show directories like `datadog-agent` or `google`.
**I would use this when** installing or locating software that isn't managed by the system package manager.

---

### Hands-on Commands

```bash
# Find the largest log files in /var/log
du -sh /var/log/* 2>/dev/null | sort -h | tail -5

# Check the system hostname config
cat /etc/hostname

# List everything in your home directory (including hidden files)
ls -la ~
```

## Part 2: Scenario-Based Practice

---

### Scenario 1: Service Not Starting

**Situation:** The `myapp` service failed to start after a server reboot.

**Step 1:**
```bash
systemctl status myapp
```
**Why:** Shows whether the service is active, failed, or stopped, and gives a brief error snippet.

**Step 2:**
```bash
journalctl -u myapp -n 50
```
**Why:** Displays the last 50 log lines for `myapp` so I can see the exact error message causing the failure.

**Step 3:**
```bash
systemctl is-enabled myapp
```
**Why:** Confirms if the service is set to start automatically on boot; if it says `disabled`, that's why it didn't come back after reboot.

**Step 4:**
```bash
systemctl start myapp && systemctl status myapp
```
**Why:** Attempt to start the service manually and immediately check if it comes up successfully or fails again.

---

### Scenario 2: High CPU Usage

**Situation:** The application server is slow; I need to find which process is hogging CPU.

**Step 1:**
```bash
top
```
**Why:** Shows a live, auto-refreshing view of all processes sorted by CPU usage. Press `q` to quit. The top entry is the culprit.

**Step 2:**
```bash
ps aux --sort=-%cpu | head -10
```
**Why:** Gives a static snapshot of the top 10 CPU-consuming processes with their PIDs and command names — easier to read than `top` for a quick check.

**Step 3:** Note the PID of the offending process, then inspect further:
```bash
ls -l /proc/<PID>/exe
```
**Why:** Reveals the actual binary path behind the process, helpful if the name in `top` is ambiguous.

---

### Scenario 3: Finding Service Logs

**Situation:** A developer asks where the logs for the `docker` service are.

**Step 1:**
```bash
systemctl status docker
```
**Why:** Quick sanity check — confirms docker is systemd-managed and shows the last few log lines.

**Step 2:**
```bash
journalctl -u docker -n 50
```
**Why:** Retrieves the last 50 lines from the systemd journal for docker. This is the primary log source for systemd-managed services.

**Step 3:**
```bash
journalctl -u docker -f
```
**Why:** Follows the log in real-time (like `tail -f`) — useful when reproducing an issue to watch it happen live.

---

### Scenario 4: File Permissions Issue

**Situation:** Running `./backup.sh` returns `Permission denied`.

**Step 1:** Check current permissions
```bash
ls -l /home/user/backup.sh
```
**Look for:** `-rw-r--r--` — no `x` bit means the file is not executable.

**Step 2:** Add execute permission
```bash
chmod +x /home/user/backup.sh
```
**Why:** Adds the execute (`x`) bit for the owner (and group/others by default with `+x`).

**Step 3:** Verify the change
```bash
ls -l /home/user/backup.sh
```
**Look for:** `-rwxr-xr-x` — the `x` bits confirm the file is now executable.

**Step 4:** Run the script
```bash
./backup.sh
```
**Why:** Confirms the permission fix worked and the script runs without errors.

## Why This Matters for DevOps

Knowing the Linux file system hierarchy means I always know where to look — logs in `/var/log`, configs in `/etc`, third-party tools in `/opt`. Combined with scenario-based troubleshooting (checking service status → reading logs → fixing permissions), this forms the foundation of real-world incident response, deployment debugging, and automation scripting.
